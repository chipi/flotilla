## Decisions worth knowing

- **The examples ship `v1` only** (heartbeat and triage keep the `v2` they have). The e2e generates
  the shadows (v1's files plus a marker file, so the hash differs): the real example code runs as a
  shadow, and a version that behaves differently is the installation's to write.
- **The catalogue is structural, not a flag.** A type the scheduler and the other consumers cannot
  be handed beats a list every consumer must remember to read; a test lists the files that may.
- **Triage on a station gets a new entry point,** so the old `orchestrator.py` and `triage.py` paths
  stay byte for byte what live runs use. What the repo can prove is request-equivalence against a
  scripted endpoint; decision parity on real captures is the installation's
  `gate_stations_replay.py`.
- **The e2e's no-effect sections are `noeffect`,** which is `versions`, `hostagent`, `versionscase`,
  `shadows`, `stations` and `matrix`: the shadow monitor's pairs read the case the
  versions-on-a-case section leaves open on the host agent's target, so the proof is not independent
  of them.
- **Slack and the hosts are recorded by what exists.** flotillad's `slack` section names the
  stand-in host as the connector; its agent is no connector, so it logs each plan flotillad asks it
  to post (`not its Slack connector`), and an e2e check waits for that line while a plan waits for
  approval. The matrix then compares the store's `slack_asks` and `brief` rows and that host's audit
  log before and after all the shadow runs. No Slack API stand-in was built (a websocket would be a
  mechanism of its own).

## Found on the way

- **The first e2e run after the flip failed four checks, all caused by step 5's own commits:** the
  ledger replay and the namespace check used the worker's own token on the listener (401); the
  `-check` row expected `accept` as the default; the stations section counted every text in the
  store and triage's station added one. Fixed in `29b466e`.
- **`gate_ledger_backend_replay.py` cannot run under `required` with any token.** It writes rows,
  which only a worker's own token (honoured by `accept`) or a run's own token may; the operator's is
  import and read only, and a run's is confined to its routine's namespace, so the replay's fresh
  namespaces would collapse into one. The `--token-file` option the earlier commit gave it was
  therefore wrong for its writes. Its usage text and the compose README now say it runs against a
  flotillad in `accept`, and the e2e starts one. This is a decision for the operator if the replay
  is still wanted under `required` (ADR-0021, alternatives).
- **`-check` refused the installation's own old workers, so no upgrade could pass it** (found in
  review after the first round). The capability check ran before `-check` returned, deploy.sh runs
  `-check` while the previous tag's workers still answer and `up` is later, so every real upgrade
  would have died before `up`. `-check` now reports a worker without the capability and passes; the
  start refuses it (`enforceRunTokenCaps`), flotillad depends on every worker its config may name
  (the candidate was missing from `depends_on`), and the e2e runs the upgrade: an old worker during
  `-check` (passes, reported), the start refusing it, the worker replaced by the real image, and
  required holding after.
- **A shadow worker only this stack has failed with HTTP 407** until flotillad's `NO_PROXY` named
  it: flotillad reaches workers directly, and the compose file's list is the shipped workers'.
- **`flotilla-e2e-host-audit` could not be removed** after a run (the audit log is append-only, so
  the volume's file resists `volume rm`); it is left by every run, and the matrix reads the host's
  log from it.

## Not a strict no-op for the installation

- **A flotillad with no `run_tokens` line now means `required`.** Anything run by hand inside a
  worker with the worker's own token stops working: `ledger_sync import` and `check`, and the
  replay. The upgrade is one deploy: `-check` runs while the previous tag's workers still answer and
  only reports them (`NOT run-token capable`); `up` recreates the local workers with flotillad (it
  waits for each, the candidate included); the start then refuses any worker still without
  `run_token` in `/healthz`. The remote host agents and workers are upgraded after the mini,
  flotillad first: until then their links are refused under required, and an agent of this build is
  refused by a flotillad of the previous build (`json: unknown field "caps"`). Set `run_tokens:
  accept` for one release to keep the worker-token fallback for workers; it does not bridge the
  agents.
- **The compose files no longer give the workers
  `ROUTINE_FLOTILLA_API_TOKEN_FILE=/run/flotilla/worker.token`.** A run's own token overrides it, so
  a routine's ledger calls and `case_review`'s reads are unchanged.
- **The flotillad image holds the examples twice,** and `examples_dir` is unset until the
  installation sets it: it sees no example until then.
- **A routine the installation lists in `disabled_routines` no longer runs by hand** (`RunNow`:
  409).
- **The installation's flat routines change in nothing but what `required` changes:** command, env,
  budget, hashes, autonomy and the runenv golden are as before (the move-equivalence tests hold it).
- **No schema change:** still 32.

## The e2e (C6, C7)

`E2E_SECTIONS=a,b` runs only those sections (the build, the config and `up` always run); unset runs
all. `deploy/e2e/make_shadows.py` generates the shadows, `matrix.py` runs them (a row per routine,
ending `NOEFFECT PASS n / SKIP m (reasons) / FAIL k`), `extend_state.py` adds a key and a column v1
does not know, `make_probes.py` writes a run-token probe per worker class, and `old_worker.py` is a
worker with no `run_token` in its health. Before the matrix's shadows exist, `matrix.py drive` gives
every routine work and a live run: `clone_records.py` copies a record into each business store so
each scan opens new cases, the examples' actions and acting routines go to propose, and the plans
that wait are approved round after round, so the acting routines run and their checks after them.
The matrix covers 24 routines (every example on the `ops-read` worker) and `e2e/hostile-brief`; 19
of the 24 got a real shadow run, and `triage/cycle` has a state row.

`e2e/hostile-brief` is the hostile attempt on the brief and Slack: its v2 reports a detection with a
plan that, on the live path, waits for approval (and is offered to Slack) and a brief line. The
`brief` cell compares the written briefs and the summary events they are made from, the `slack` cell
the asks and the cases awaiting approval.

Who calls the workers' listener, traced for the open item: the triage fleet's ledger
(`runtime/ledger.py`) and `ops/case_review.py` (`ops/flotilla_api.py`) are the only code that does.
The compose file sets the listener's address (`ROUTINE_FLOTILLA_API_URL`) on the triage, candidate,
shadow, ops-read and ops-act-host workers only; the bugfix, bugfix-act and marketing workers and
`deploy/remote` set none, so no routine of theirs can reach it (pinned by
`cmd/flotillad/compose_test.go`). A remote worker gets its run's token in the JSON request through
its link (`hostlink.RunRemote`, `worker.Request.api_token`) and writes it to a file like any worker;
the e2e's remote probe proves that and that the worker's own token is refused, under `required`.

Mutants, each seen red on the check it must break (the e2e logs are under the coordinator's
scratchpad, `e2e_mut_<name>.log`):

| Mutant | Fault | Red on |
| --- | --- | --- |
| `noeffect-vacuous` | crm/scan's shadow runs `true` and decides nothing | `shadow FAIL: shadow_runs done 1, decision records 0`, `E2E FAIL (1)` |
| `matrix-live-write` | a shadow writes a folder the live worker shares | `unchanged FAIL: a worker state file changed` |
| `required-fallback` | a worker's own token is a caller of the listener again | the run-token probe on every worker class |
| `caps-skip` | any worker or agent counts as run-token capable | `an old worker under required`, `E2E FAIL (1)` |
| `shadow-write-cred` | a write credential in the shadow worker's read environment | `hostile shadow` and 13 more |
| `shadow-egress-open` | the shadow's proxy allows the write host | `a shadow reached GitHub`, `E2E FAIL (1)` |
| `shadow-live-handler` | a shadow's report is also handled by the live path | `brief=FAIL slack=FAIL`, the cases cell, hostile-brief's `unchanged` |

The first version of the matrix's shadow cell counted any record, and `noeffect-vacuous` stayed
green on it (`run.started` is written for every shadow run); it counts decisions now. Unit mutants:
`listenerCallers` with a worker-token caller left in, the examples catalogue appended to flotillad's
routines (the real start refuses: `example-bugfix/fix needs worker "bugfix-fix"`), an example's
freshness pushed (the metrics test), a `ROUTINE_FLOTILLA_API_URL` on the bugfix worker (the compose
test), the required list without `no-effect?` and the job renamed (the deploy and job-name tests).
